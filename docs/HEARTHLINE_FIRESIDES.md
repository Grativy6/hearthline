# Hearthline Firesides

> **Hearthline carries the work. The Scribes carry questions she does not need to hold all at once.**

| Field | Value |
|---|---|
| Version | `0.6` |
| Status | Candidate successor design vocabulary — pending steward review |
| Implementation | Not asserted by this document |
| Author and steward | Christopher D. Pang |

A **Hearthline Fireside** is a bounded consultation arrangement in which Hearthline continues the primary task while one or more **Scribe Sparks** follow an authorized, coordinator-emitted **Run Trail** through separately declared lenses.

The arrangement is coordinated but asymmetric. Hearthline remains on the task's critical path. Scribes externalize specialized vigilance, leave source-bound notes, and offer advisory material for consultation. They do not become co-owners of the task, decision makers, independent authorities, or a quorum.

Version `0.6` aligns Firesides with the candidate
[Task Triad](HEARTHLINE_TASK_TRIADS.md) selected-carry successor. The earlier
paired arrangement and version `0.5`'s Thulia-first three-member relay remain
preserved ancestry in [Task Triads and Homecoming](HEARTHLINE_HOMECOMING.md).
The current candidate gives Worker, Task-Keeper/Heartbeat-Keeper, and Ledger
Scribe/Ledger-Keeper one job each, separate accounts, statuses, heartbeat
contracts, Homes, seals, and returns. Each separately `SEALED` and `VALID`
member bundle returns to the exact Hearthline task intake; only Hearthline's
later immutable Carry Selection crosses to Thulia.

Version `0.4` remains the adopted account-custody ancestor: every Field Notes,
Ember, and Static ledger belongs to a declared task or representation account,
and a Scribe receives an exclusive bounded write lane rather than ownership.
The candidate successor preserves Hearthline orchestration, Thulia custody and
Systemic Friction, and Gloss's stateless deterministic turn as distinct jobs.

## Fireside surfaces

| Surface | What it carries | Default effect on later work |
|---|---|---|
| **Run Trail** | Ordered, committed, inspectable task events | Available only through the authorized view |
| **Field Notes** | One Scribe's observations, interpretations, questions, warnings, and residuals | Advisory within the current run |
| **Embers** | Anything that Scribe recommends considering for later carry | `PROPOSED_NOT_ADOPTED` |
| **Static** | One account's isolated, versioned, reversible shorthand | Governs only records that name its exact active version |
| **Bridge Gloss** | A numbered, source-bound reconstruction of selected sending-account Static | Derivative candidate material for one named recipient and purpose |
| **Triad Return Manifest** | Exactly three member slots and their separate valid, invalid, missing, stale, or unknown dispositions | Required inspection index; never a merged result or vote |
| **Carry Selection** | Hearthline's immutable, complete semantic disposition of every admitted item and typed exception | Selected projection only; not retention classification or deletion authority |
| **Translation Board** | Task-scoped, schema- and size-bounded shorthand requests, mappings, rule traces, and writer-separated receipts | Only Hearthline may mark an exact mapping `SERVICEABLE` for the active root task |
| **Selected-carry handoff store** | Exact bytes durably accepted by Thulia for the remaining route | May satisfy one inspection-access-close gate; not canonical retention |
| **Readable Carry Envelope** | Thulia's selected-projection-only return after any exact Gloss turn | Candidate input to Hearthline; never unselected raw member payload |
| **Carry Manifest** | Exact reviewed material selected for a declared continuation | Candidate input until separately loaded |
| **Load receipt** | Exact material actually introduced into one active context | Evidence of that bounded load only |
| **Home Record** | One Spark's declared return boundary, permitted bundle, and reconciliation rule | A return address, not a grant or shared memory |
| **Spark Heartbeat Contract** | Task-shaped timing assumption, bounded cadence, wake triggers, remaining limits, and suspension/resume rules | Liveness discipline only; cannot renew scope or authority |
| **Task Line** | Controller-owned immutable task identity, Goal Lineage, `NARROWS` Purpose Projection, exact scope, and epochs observed by the Task-Keeper | A reference boundary, not ownership of the task |
| **Completion Contract** | Frozen finish, blocker, cancellation, and handoff conditions for one task | A comparison rule, not a source of truth or success |
| **Task-Boundary Witness** | Task-Keeper's typed comparison of committed evidence and returns against the Completion Contract | `MATCHED`, `NOT_MATCHED`, or `UNKNOWN`; never task success by itself |
| **Homecoming records** | Separate Return, Reconciliation, and Context-Close Receipts beneath one Homecoming identity | Evidence of each bounded transition only; reconciliation is not closure |

These surfaces are related but not interchangeable. A Field Note is not
automatically an Ember. An Ember is not automatically selected. A Carry
Selection is not Systemic Friction. Thulia's durable acceptance is not a
canonical store effect. A Carry Manifest is not automatically loaded. A load
does not grant permission or authority.

## Scribe is a job, not a fourth role

Every Scribe remains exactly one of the three Spark roles: Seeker, Explorer, or Handler.

- A **Scribe Seeker** may follow only the brokered metadata projection allowed to a Seeker.
- A **Scribe Explorer** may read the authorized content projection and emit notes or proposals, but remains read-only toward the task environment.
- A **Scribe Handler** may mutate only the expressly granted targets. Scribe status adds no mutation right.

A control-owned recorder may persist a Seeker's or Explorer's emitted notes in
the assigned representation account without granting the Spark direct write
access. If a Spark itself is to write durable records, its Handler grant must
name the exact account lane and permitted append operations. The account owns
the ledger; a controller-observed candidate seal closes the execution/write
lane, and Homecoming later moves only the valid sealed bundle.

The candidate [Task Triad](HEARTHLINE_TASK_TRIADS.md) designates one Scribe as
the **Ledger Scribe Spark**, also called the **Ledger-Keeper**, beside a primary
Work Spark and a separate Task-Keeper. Hearthline nominates only Work Spark and
Task-Keeper; Thulia independently nominates only Ledger-Keeper. The controller
allocates and reserves the separate records and freezes one complete offer and
digest. Each provider then commits only its own final intent over that offer,
and the controller atomically consumes both intents and reservations or binds
nothing. Provisioning does not make
Hearthline or Thulia the task's terminal authority. Here **provisioning** means
interface-exclusive selection and commitment of one seat's intent; the
canonical controller or store remains the sole mechanical allocator of
identities, grants, bindings, and receipts.

The Work Spark carries the bounded doing; the Task-Keeper carries the frozen
Task Line and Completion Contract; the Ledger Scribe carries the representation
and coverage job. **Task-Keeper** and **Ledger-Keeper** are jobs, not new Spark
roles. Each remains a Seeker, Explorer, or Handler under its own aperture and
grant. Each Spark receives one job. The trio is one parent objective projected
into three sibling member tasks, not one helper with three duties and not a
shared will hidden behind three names.

Purpose also does not follow custody. Christopher's declared goal narrows to
Hearthline's objective; Hearthline's objective narrows separately to the Trio
Task Line and Thulia's mediation objective; the Trio Task Line narrows to the
three member jobs. Every edge is a recorded `NARROWS` Purpose Projection.
Thulia's co-formation of the Ledger-Keeper neither makes the Trio her child nor
passes authority through her, and the members' later return to Hearthline does
not give Hearthline Thulia's provisioning lane.

The Ledger Scribe job narrows the Scribe toward externalized, committed,
grant-filtered summaries, observable outcomes, residuals, and target-bound
representation proposals in its assigned representation-account lineage. It
does not let the Scribe choose primary actions, read hidden reasoning, approve
proposals it produced, allocate or write the Work task account's Static, alter
the Completion Contract, or inherit another member's grant. The earlier paired
default remains attributable design ancestry; it is not silently rewritten as
having included a Task-Keeper.

The Task-Keeper, also called **Heartbeat-Keeper** when its cadence-facing
surface is emphasized, reads only the committed task-boundary projection named
in its own grant. It keeps the Task Line from drifting, observes due-work,
suspension, blocker, and candidate-seal boundaries, and emits a typed
Task-Boundary Witness at the frozen comparison boundary from only the
predeclared committed references it may observe. Its predicate may not depend
on later Hearthline intake, inspection, Carry Selection, Thulia handoff, or
readable return.
It does not perform the Work job, write the Ledger Scribe's account, interpret
uncommitted material, keep a process alive, schedule a model, manufacture
terminal authority, or decide whether the underlying task truly succeeded.

## Declared lenses

A Scribe receives a visible, versioned lens that narrows what it is asked to notice. A lens is not a hidden personality and does not widen the Spark's aperture, stop power, consequence ceiling, or authority.

| Lens | Declared attention |
|---|---|
| **Red-team** | Challenges decisions, assumptions, crossings, failure behavior, and untested success claims |
| **Prime-shell** | Locates declared load-bearing prime shells or analogous structural premises and identifies what depends on them |
| **Divergence** | Prioritizes checks whose possible results separate the greatest number of live branches |
| **Trace** | Watches provenance, source class, unresolved obligations, authority ceilings, residuals, and reopening paths |
| **Static** | Watches canonical entries, recurring equivalence candidates, negative constraints, residuals, and possible grammar or codebook deltas |

Additional lenses may be added as newly numbered Spark profile versions. A lens may recommend attention; it cannot establish truth, priority, permission, or a decision merely by being assigned.

An ordinary instance may be named by lens, job, and role—for example, **Prime-Shell Scribe Explorer (`SPARK-000012`)**. A long-lived Spark may also receive a unique display name while its ordered identity, role, lens, source, and grant remain visible.

## The committed Run Trail

The coordinator is the sole canonical Run Trail writer. After a task event is durably accepted, the coordinator may emit an immutable, filtered event envelope to each Scribe according to that Scribe's role and grant.

Here, **committed** means fixed in the declared Run Trail. It does not mean true, approved, executed, authorized, committed to Git, or endorsed by Hearthline or Christopher. The Run Trail contains externalized, inspectable records—not hidden chain-of-thought, private scratch reasoning, or an inference that a model experienced an event.

Every trail event receives the next ordered event number and should bind at least:

- Fireside, run, and event identities;
- its predecessor or previous trail-head digest;
- event type, observation epoch, source references, and content digest;
- the declared view or redaction policy applied for each recipient; and
- whether it records an intention, proposal, attempted action, completed effect, observation, or result.

Scribes consume coordinator-emitted committed events or immutable snapshots. They do not live-tail a mutable operational database, interpret uncommitted objects as events, or co-write the task ledger.

## Coverage and non-blocking work

Each Scribe binds its output to an exact coverage watermark: the run, authorized view, inclusive event range, and terminal event or checkpoint it actually observed. It must not imply awareness of later events or of material excluded from its view.

Hearthline can complete or continue the primary task without waiting for every Scribe. Note completion remains separate from task completion:

- `COMPLETE_THROUGH_EVENT_N` means complete only for the declared view through that event;
- `INCOMPLETE_THROUGH_EVENT_N` preserves known gaps or an interrupted pass; and
- no Scribe status automatically changes task status.

The Task-Keeper's status is separate again. `MATCHED` reports only that the
committed material in its declared view meets the frozen Completion Contract.
`NOT_MATCHED` and `UNKNOWN` preserve a failed or unavailable comparison. None
of the three statuses creates an authority-sourced task result, and a complete
Ledger-Keeper page cannot turn an incomplete or failed Work return into
success. Hearthline may request a witness, but cannot manufacture one without
the separately provisioned Task-Keeper and its committed inputs.

When a task spans several event streams, coverage remains a per-stream vector rather than being collapsed into one misleading maximum.

A Scribe may raise an advisory warning during the run. It interrupts Hearthline only when a separately declared stop condition requires that response. Silence is not approval, and a delayed note does not retroactively become an earlier decision.

## Separate accounts, separate triad lanes

Every Scribe receives a separate context, credential boundary, and exclusive
bounded lane in one representation account. That account keeps its Field Notes,
Embers, Static, and caches. Scribes do not directly read or write one another's
account ledgers and do not silently exchange Static.

Inside a Task Triad, each Spark emits only material eligible for its declared
lane: Work material for the task account, boundary status for the Task-Keeper
account, and representation material for the Ledger Scribe account. The
canonical recorder persists read-only Spark output; a Spark writes durable
records directly only under the exact Handler grant that permits it. Their Run
Trail projections may share committed event references, but their payload
ledgers, coverage vectors, statuses, budgets, and Homecoming receipts remain
separate.

Several Scribes may follow the same Run Trail through different lenses. Their separate first passes should not consume one another's notes unless an explicit reconciliation stage opens that material. This preserves the declared difference between lenses without pretending they are statistically or epistemically independent.

Agreement among Scribes using the same trail, source lineage, model family, prompt ancestry, or coordinating process is reported as **convergence across declared lenses**, not independent corroboration, a vote, or a quorum. Disagreement remains visible for Hearthline or the authorized reviewer to examine.

## Thulia at the Fireside

[**Thulia**](HEARTHLINE_THULIA.md), Hearthline's pet owl and Owl Scribe, is not
a fourth Spark role, Scribe Spark, analytic lens, or second Hearthline. Her
candidate surface has three bounded duties: provision only Ledger-Keeper seats;
custody separate `H_TO_T_CARRY` and `T_TO_H_READABLE` lanes; and custody
separate `T_TO_GLOSS_TURN` and `GLOSS_TO_T_RESULT` lanes. She does not inspect
the primary work, reconcile Scribe advice, choose semantic carry, make
shorthand serviceable, recalculate a Task-Boundary Witness, or write
receiving-account Static.

For a Task Triad, the three raw member bundles bypass Thulia. Each separately
`SEALED` and `VALID` bundle returns by a controller/store-mediated transaction
to the exact commissioning Hearthline task intake as
`RETURN_PENDING_HEARTHLINE`. Thulia's provisioning of the Ledger-Keeper grants
her no access to that bundle. Hearthline may inspect the complete three-slot
return manifest only under a bounded projection and then seal one immutable,
complete Carry Selection. Only that selected projection enters Thulia's Hearth
Perch; a typed omission or loss remains visible to her retention gate without
exposing an unselected raw payload.

If selected carry contains Static that needs a fixed translation, Hearthline
authors a constrained request on the external, task-scoped Translation Board.
Only Hearthline may mark an exact mapping `SERVICEABLE` for the active root
task. Thulia custodies the pinned request and receipts but does not choose the
meaning. [Gloss](HEARTHLINE_GLOSS.md) performs one stateless deterministic
turn only after a fresh external readiness check for that exact turn. Gloss is
not a Spark and has no heartbeat, support trio, ledger, history, or persistent
readiness. Only `COMMITTED_SUCCESS` or `COMMITTED_SNAG` attests placement of a
deterministic mark; unknown or known-no-commit states remain separately typed.

Thulia returns a Readable Carry Envelope containing only the authorized
selected projection, translation receipts, and typed exceptions. Only after
that readable boundary may she apply **Systemic Friction** under a separate
retention grant. Hearthline's semantic selection, inspection-access release,
Thulia's friction classification, a canonical Atomic Edge Promotion, and
source recoverability are independent facts. Hearthline may request review but
cannot take over Thulia's classification; Thulia cannot use retention custody
to change Hearthline's chosen meaning.

## Field Notes and Embers

Field Notes are current-run working records. Each newly opened page receives the next ordered notes number and binds the Scribe, lens and profile version, Fireside and run, authorized trail view, opening boundary, governing Static version, and predecessor page.

An **Ember** is an inert carry candidate. A Scribe may propose any content within its authorized aperture: a fact, hypothesis, warning, failed path, unfinished obligation, preference, useful routine, source pointer, or proposed Static change. “Anything” describes the payload type, not authority.

Each Ember receives its own ordered number and an envelope recording:

- origin Spark, profile, Fireside, run, Field Notes page, and coverage watermark;
- source references, declared observation or interpretation status, uncertainty, and residuals;
- sensitivity and permitted audience;
- reason for possible carry and intended destination or scope;
- payload and digest; and
- current disposition and every later disposition receipt.

The carry gate is strict:

`PROPOSED != CONSULTED != CARRY_APPROVED != LOADED`

- **Proposed** records the Ember as `PROPOSED_NOT_ADOPTED`.
- **Consulted** records who or what examined the exact candidate and under which grant.
- **Carry-approved** records a bounded selection by the actor permitted to make that continuation choice.
- **Loaded** records the exact bytes or structured content actually introduced into a named active context.

No stage silently implies the next. Consultation may end in partial adoption, deferral, revision, or rejection. Carry approval is not external consent, permission, or authorization. Only material explicitly loaded enters the resumed context. No Spark approves its own proposal merely by repeating it, verifying it, or recording successful later results.

## Tending the Fireside

Hearthline may work fluidly inside the unchanged task grant while Scribes carry specialized questions beside her. When a declared uncertainty, cadence, checkpoint, warning, or consequential boundary calls for review, Hearthline may **tend the Fireside**:

1. Pause at an exact committed Run Trail boundary.
2. Identify each consulted Scribe and its actual coverage watermark.
3. Seal the current Field Notes page with its ordered identity, digest, completion state, and governing Static version.
4. Consult the authorized Field Notes and Embers under the bounded Hearthline inspection grant; keep observation, interpretation, recommendation, permission, and authorization distinct.
5. Seal a complete Carry Selection stating what Hearthline took up, condensed, knowingly left out of active carry, or left unresolved, without rewriting the source pages.
6. For selected material that requires translation, author a constrained Translation Board request bound to the exact sending version, destination, audience, purpose, coverage, lexicon generation, and task expiry; Hearthline alone records whether the returned mapping is task-serviceable.
7. Receive any Thulia-routed Readable Carry and exact Bridge Glosses, preserving snag, omission, receipt, and unknown states without treating a deterministic output as semantic approval.
8. Evaluate any proposed Static revision under the exact reconstruction rule in [Hearthline Static](HEARTHLINE_STATIC.md).
9. If a same-ledger revision is admitted by that account's authorized writer, append it under its already allocated version number and add a separately numbered activation receipt. A cross-account target-bound delta receives no target version until the target account's authorized writer admits and allocates it after direction-bound carry. Do not alter either predecessor.
10. Open the next numbered blank Field Notes page under the active Static version, load only explicitly selected material with its load receipt, and resume within the original remaining grant and limits.

The page becomes blank; the history does not. Pending Embers, uncompressed residuals, declined advice, incomplete notes, and reopening handles remain separately addressable.

Improved shorthand changes representation only. It cannot widen Hearthline's discretion beyond the current grant, alter instruction precedence or stop conditions, create a capability, or manufacture authority. A trial Static revision may be used within the current run only when a predeclared adaptive-Static grant and the required verification and activation receipts permit it. Carry into a later run remains a separate reviewed decision.

## Closing the Fireside and coming home

When a bounded run ends, every participating Spark follows its own declared
[Homecoming](HEARTHLINE_HOMECOMING.md) route. In the candidate Task Triad, the
Work Spark returns its task artifact and task-local status; the Ledger Scribe
returns notes, negative constraints, residuals, and one typed representation
disposition (`static_delta`, coverage-qualified `NO_LEDGER_DELTA`,
`LEDGER_DELTA_INCOMPLETE`, or `LEDGER_COVERAGE_UNKNOWN`); and the Task-Keeper
returns `MATCHED`, `NOT_MATCHED`, or `UNKNOWN` in a Task-Boundary Witness. The
three bundles share a frozen task reference but remain separately sealed,
validated, moved, and receipted. Only a controller-observed `SEALED` plus
`VALID` bundle may enter `RETURN_PENDING_HEARTHLINE`; invalid,
validity-unknown, missing, stale, partial, or emission-unknown returns remain
typed as such. Every eligible bundle moves to the exact commissioning
Hearthline task intake under its own preallocated transaction. It never returns
through Thulia merely because Thulia provisioned the Ledger-Keeper.

The controller seals a complete **Triad Return Manifest** with exactly three
member slots. Hearthline then inspects the admitted references under a bounded
grant and seals an immutable **Carry Selection** that accounts for every item
and exception. A `MATCHED` witness, complete Scribe coverage, reconciled
Homecoming, complete manifest, or well-formed Carry Selection is not the task's
authoritative result and cannot promote it to success.

Only the selected projection crosses `H_TO_T_CARRY`. Thulia's durable receipt
does not imply agreement, translation, Systemic Friction, store commitment, or
readable return. A separate selected-carry handoff-store commit must preserve
the identical accepted bytes before the controller may attempt to close
Hearthline's raw inspection projection. `RAW_ACCESS_DROPPED` means only that
the declared task-scoped raw read surface and its locators were detached. It
does not claim source deletion, physical erasure, global unrecoverability, or
literal model forgetting; an ambiguous close remains
`CLOSE_OUTCOME_UNKNOWN` and is reconciled under the same transaction identity.

Any translation and readable return use four distinct direction-bound lanes:

- `H_TO_T_CARRY` carries the sealed selected projection to Thulia;
- `T_TO_GLOSS_TURN` carries one pinned request after per-turn readiness;
- `GLOSS_TO_T_RESULT` carries the deterministic result or typed snag; and
- `T_TO_H_READABLE` carries the selected-projection-only Readable Carry
  Envelope back to the exact Hearthline task intake.

Each lane has its own grant, digest, idempotency key, emission observation,
target receipt, and exact unknown-outcome query. No receipt fills another
lane. Gloss readiness expires with one exact turn and is not liveness. A late
or changed result requires a separately numbered successor; no actor resends
automatically after an ambiguous emission.

Each Spark Heartbeat Contract ends at its own completion, declared terminal
blocker, revocation, expiry, or return boundary. Before a nonterminal blocker or
no-due-work boundary enters `SPARK_SUSPENDED`, the canonical controller appends
exactly one contract-bounded Pulse Receipt. The Spark records no further task
action until a valid Resume Receipt. A Scribe may use only a predeclared grace
interval to seal its actual coverage. It does not continue indefinitely because
the task was important or because later notes might be useful. Every issued
pulse is allocated and appended by the canonical controller or store.

`HOMECOMING:RETURNED`, `HOMECOMING:RECONCILED`, and
`HOMECOMING:CONTEXT_CLOSED` are separate states with separate controller-owned
receipts. Arrival does not establish that the bundle matched the dispatch-pinned
Home Record and current authorization checks; reconciliation does not establish
task success, carry approval, or closure; and a member Context-Close Receipt
does not erase the run or close Hearthline's later inspection projection.
`HOMECOMING:CONTEXT_CLOSED` is not PAL or A15 closure. Unknown or partial
returns remain visible and are not replayed automatically.

After any readable return, Thulia alone may apply Systemic Friction under a
current retention grant. `PRUNE_ELIGIBLE` changes no bytes. A canonical
controller or separately authorized writer later performs any exact Atomic
Edge Promotion and records its effect independently from source
recoverability. Thus selected-carry survival for inspection release and later
canonical compaction, archive, or pruning are two different storage edges.

## Ordered lineage and failure behavior

[Hearthline Ordered Lineage](HEARTHLINE_ORDERED_LINEAGE.md) governs every Spark,
profile version, Task Triad, Task Line, Completion Contract, Task-Boundary
Witness, Triad Return Manifest, member-return transaction, inspection context,
Carry Selection, selected-carry handoff store, Translation Board generation and
entry, Readable Carry Envelope, Home Record, Spark Heartbeat Contract, Pulse
Receipt, Static version, Field Notes page, Ember, Fireside, run, trail event,
Owl profile, Perch, translation request, Bridge Gloss, delivery receipt,
Homecoming record, Carry Manifest, retention classification, Atomic Edge
Promotion, activation, and load receipt.

Numbers are allocated before use, increase within their named series, and are never reused, reassigned, renumbered, or overwritten. Rejection, failure, retirement, or an interrupted reservation leaves its original number and status visible. Corrections append successors.

If a coordinator cannot establish the active Static version, exact Run Trail head, ordered identity, coverage watermark, or current grant, the affected consultation or refresh fails closed. Recovery preserves gaps and predecessor records rather than rolling counters backward or reconstructing a cleaner history.

## Lore and implementation boundary

Earlier versions adopt Fireside, Scribe, Run Trail, Field Notes, Embers, Bridge
Gloss, and tending as Hearthline lore and design vocabulary. Version `0.6`
proposes their selected-carry Task Triad integration as a candidate successor
pending steward review. Version `0.5` remains recoverable candidate ancestry;
it is not silently rewritten to have used this return route. This document does
not instantiate a worker, run concurrent models, implement an event stream,
create Thulia's roost, create memory, allocate an operational number, make a
model forget, activate Hearthline, or authorize a task.

Any implementation must separately test role projections, controller-owned
single-writer append and allocation, committed-event filtering, idempotent
submissions, gap detection, coverage watermarks and dispositions, independent
Work, witness, and note status, separate Task Lines, Completion Contracts,
Task-Boundary Witnesses, triad-member accounts, Home Records, frozen Static
references, and Spark Heartbeat Contracts, suspension without busy-polling,
terminal and nonterminal blockers, missed-pulse behavior, resume revalidation,
bounded Scribe grace, returned/reconciled/context-closed separation, fixed-arity
controller-only binding, disjoint Hearthline/Thulia provisioning intents,
separate `SEALED` and `VALID` member admission to the exact Hearthline task
intake, per-member idempotent transactions, three-slot Return Manifest,
bounded inspection, complete immutable Carry Selection, selected-carry
handoff-store survival, raw-access drop without a forgetting claim,
writer-separated and root-task-scoped Translation Board lanes, Hearthline-only
serviceability, four direction-bound translation and carry crossings,
Readable Carry axes, target-owned receipt, relay idempotency, rejection of
`MATCHED` or complete coverage as task success,
Scribe and Perch isolation, no Gloss heartbeat or persistent readiness,
exact Bridge Gloss reconstruction, target-bound account custody,
recipient-specific disclosure, no cross-account Static import, carry-gate
transitions, inspection-release/retention/effect/recoverability separation,
Thulia-only Systemic Friction, Atomic Edge Promotion effect ownership,
refresh barriers, activation ordering, crash recovery, privacy handling, and
revocation.

Hearthline and Scribes are AI tools and system concepts, not persons, co-authors, independent witnesses, or authorities. Their named lenses and preserved work do not establish consciousness, emotion, ownership, consent, standing, or permission.
