## What changed

Toolkit 0.3.0 uses shared foundation 0.2.0. Separate PAL v2.4 profiles compare
declared work recovery, source content, requirements, current grant reports
and resource accounts. Five published source artifacts have exact identities
and file hashes. The PAL 2.3 account checker remains available.

An opt-in checkpoint bridge uses the existing TETHER and scoped ledger.
Freezing preserves explicit work, source and requirement bindings. Reading
recovers that work without performing a resume check. Reopening appends a
review, keeping failed and successful attempts visible. Known recorded costs
cannot disappear or decrease on restart. An earlier unknown cost can acquire
a declared value while its original observation remains in history.

## Why

Christopher requested the Hearthline repository updates after PAL v2.4.
SC-22 distinguishes exact work recovery from answer preservation, continuation
equivalence, source identity, applicability, authorization and resources.
Recovering a cursor or answer cannot silently restore all those other fields.

## Preserved boundaries

This is a finite implementation profile, not blanket PAL conformance. It
does not claim future continuation equivalence or a physical entropy result.
O63-O65 remain OPEN in the published source. T73-T75 are specifications;
local test observations are separately scoped implementation evidence.
PAL 2.3 and the PAL 2.2-oriented preview retain their identities and earlier
receipt meanings. MIND, TIES and CHARTER remain separately sourced.
Founding orientation, templates, selective correction and heartbeat limits
remain intact. Duplicate TETHER source identities now remain unverified.

## Compatibility and migration

Existing TETHER records still use the existing route until explicitly given
a checkpoint. Thereafter the legacy reopen route points to checkpoint review
and cannot skip its bound conditions. A successor needs an exact predecessor
and an explicit adoption reference; that reference is a declaration, not
authenticated authority. Earlier checkpoints remain readable.
There is no automatic stored-record migration, package installation or host
activation. Foundation/core/continuity profiles receive the checkpoint tools;
optional context tools retain their existing filtering.

## Verification observations

The Windows/Python 3.12 suite passed 105 tests. The checkpoint route crosses
three real MCP processes: freeze work, recover it, hold an expired grant,
append a passing declared review, then verify the complete unchanged history
on another restart. Unit cases cover missing facts, unknown costs, immutable
bindings, typed equality, successor lineage, source ambiguity, resource
history and scope isolation. The shared adapter/foundation suite passed 93
tests and 12 subtests, including real cross-adapter MCP equivalence.

All five repository structural checks passed. The four-package wheel chain
installed offline in an isolated environment with no broken requirements;
the installed Hearthline wheel passed the three-process checkpoint route.
These observations use synthetic data and establish only the named finite contracts.
Platform CI results belong to their exact checked commit.

## Open residuals

Grants, facts, costs and evidence references remain supplied declarations.
The bridge checks their stated shape and relationship; it does not discover
all conditions, authenticate evidence, measure real resource use or allocate
resources atomically. A matching review executes no recovered work and
consumes no grant or budget. Conditions must be checked again by any host
that later performs consequential work.

## Evidence and exclusions

The source map links the published v2.4 artifacts. Canonical JSON hashes
identify supplied work/source content; raw DOCX hashes identify publication
files. Neither hash domain confers truth or authority. This change performs
no model call, training, weight update, scheduler activation, live-book
registration or installed-runtime replacement. Earlier history records keep
their original bytes and meanings.
